\title{Requirements-level reference specification of the LRE controller}
\author{}
\date{8 September 2026}

\begin{document}
\maketitle

\textbf{Source.} The specification is derived from the requirements file
\texttt{lre\_requirement\_all.txt} alone, which has 51 LRE entries and
declares four operating modes. No repository content, implementation
artefact or earlier draft was consulted. The interpretive decisions it
needed are listed in Table~\ref{tab:ambiguities}.

\textbf{Scope.} The relation below specifies the mode changes, the
handling of operator input, and the output events that go with them,
over one sensor snapshot per step. It does not define the vehicle's
dynamics, a CPA algorithm or an evasive manoeuvre. The statements
labelled A01--A17 are interpretive decisions, not claims about what the
requirements say.

\textbf{State and observations.} The modes are

\texttt{Mode\ =\ \{OCM,\ MOM,\ HCM,\ CAM\}}.

At power-up the mode is OCM; there is no separate initialisation mode.
Two optional actuator records, \texttt{lastVel} and \texttt{lastHdng},
hold the most recently emitted values and are unspecified before the
first output; the mode relation does not depend on them. {[}LRE-DM1,
DM8, FR1, Beh1; A09{]}

A step observes one input

\texttt{e\ ∈\ \{none,\ reqVel(v),\ reqHdng(h),\ reqOCM,\ reqMOM,\ reqHCM,\ endTask\}},

where \texttt{v} and \texttt{h} are reals. \texttt{none} is a step with
no operator input, not an interface event. A step whose input has no
handler in the current mode can still take an autonomous transition.
{[}LRE-ARCH2, DM6; A01, A03{]}

All derived quantities and guards in a step use the same sensor
snapshot. Table~\ref{tab:symbols} gives the symbols used below.

The four thresholds default to 1 and remain distinct parameters; a
literal \texttt{1} in the transition table is a literal, not one of
them. {[}LRE-DM4; A12{]}

For an obstacle \texttt{i} that exists, at the current depth,

\texttt{hdist(i)\ =\ sqrt(ns\_rel\_dist(i)²\ +\ ew\_rel\_dist(i)²)}

\texttt{vdist(i)\ =\ abs(depth\ −\ obs\_depth(i))}

\texttt{odist(i)\ =\ sqrt(hdist(i)²\ +\ vdist(i)²)}.

An obstacle is static exactly when both horizontal velocity components
are zero; its rate of climb plays no part. \texttt{cstc} and
\texttt{cdyn} are the static and the dynamic obstacle at minimum
\textbf{overall} distance; ties go to the smallest identifier, and
\texttt{−1} stands for an empty class, so both indices range over
\texttt{ℕ\ ∪\ \{−1\}}. {[}LRE-DM2, DM3, DM5, SF1--SF3, OP3, OP4, Var5,
Var6; A05, A06{]}

Before any guard is evaluated,

\texttt{hvel\ =\ sqrt(ns\_vel²\ +\ ew\_vel²)}

\texttt{vvel\ =\ rate\_of\_climb}

\texttt{vel\ =\ sqrt(hvel²\ +\ vvel²)}

\texttt{P\ =\ (ds\ ≤\ s)\ ∨\ (depth\ ≤\ 0)}.

\texttt{CalcCStc} runs before \texttt{CheckOPEZ}, and \texttt{CalcCDyn}
before \texttt{CalcCPA}. Everything used in a step comes from that
step's snapshot: advice emitted during the step neither replaces the
measured velocity nor causes the guards to be re-evaluated.
{[}LRE-OP1--OP5, Var1--Var8, GP1; A01{]}

When a class of obstacle is absent, let \texttt{F} be a fixed real with

\texttt{F\ \textgreater{}\ max(0,\ 1,\ s,\ H,\ V,\ D)}.

At index \texttt{−1}, \texttt{odist\ =\ hdist\ =\ vdist\ =\ F}, and the
four obstacle field accessors of DM5 are zero; these sentinel distances
do not follow the geometry above. When \texttt{cdyn\ =\ −1},
\texttt{cda\ =\ F} and \texttt{tcpa\ =\ 0}. So the absence of dynamic
obstacles never enables \texttt{C} and always enables
\texttt{cda\ ≥\ s}; the absence of static obstacles makes the obstacle
part of \texttt{P} false but leaves the \texttt{depth\ ≤\ 0} part.
{[}LRE-DM5, OP2, OP5; A07{]}

When a dynamic obstacle exists, \texttt{cda\ ≥\ 0} and
\texttt{tcpa\ ∈\ ℝ} are the results of \texttt{CalcCPA} for that step
and are taken as observations. OP5 gives no formula relating them to
position and velocity, so none is imposed: the mode relation is defined
for every admissible observation, but it does not define a function from
raw sensor values to commands. {[}LRE-OP5, Var7, Var8; A08{]}

\textbf{How to read the relation.} Table~\ref{tab:transitions} gives the relation. An input trigger requires exactly
that input. An \texttt{autonomous} trigger requires no operator event
and is eligible whatever \texttt{e} is. Guards are evaluated in the
source mode on the current snapshot.

For a step, let \texttt{E(m,e,x)} be the set of rows T02--T18 whose
source is \texttt{m}, whose input trigger (if any) matches \texttt{e},
and whose guard holds in snapshot \texttt{x}. If the set is non-empty,
exactly one of its rows is taken: the mode changes to that row's
destination and exactly its output sequence is emitted. If the set is
empty, the mode is kept and \texttt{{[}{]}} is emitted. The input is
consumed either way. There is no priority among enabled rows, and no
stuttering while a row is enabled. {[}A01--A04{]}

That is,

\texttt{R(m,e,x)\ =\ \{(destination(t),\ outputs(t))\ :\ t\ ∈\ E(m,e,x)\}}
when \texttt{E(m,e,x)\ ≠\ ∅};

\texttt{R(m,e,x)\ =\ \{(m,\ {[}{]})\}} otherwise.

Each output updates its actuator record; the other record keeps its
value. \texttt{{[}{]}} means no output event, not a zero command or a
reset. Entry advice is already in the table, so it is not emitted a
second time. Startup is the separate rule T01. {[}LRE-DM7, DM8, FR2,
FR3; A09, A10{]}

A01 & ARCH2 says guards are evaluated each step, but gives no timing
model, event/sensor order, or rule for cascading transitions. & Use an
atomic step with one coherent current sensor snapshot, fresh derived
quantities, and at most one selected transition. Evaluate
input-triggered and autonomous guards together against the source mode.
Autonomous conditions are level-triggered, not rising-edge-triggered.
Entry outputs do not cause another transition within that step. \\
A02 & Several transitions can be enabled together; the file assigns no
priority, including between operator commands, OPEZ, collision
avoidance, and caution. & Admit every enabled row as a possible
alternative, selecting exactly one. Requirement numbering and table
order confer no priority. No extra veto is inferred. This is an
explicitly nondeterministic resolution; it does not require a fixed
safety or operator priority. \\
A03 & There is no event-queue, retry, or blocked-request policy. Beh19
explicitly excludes some input handling but does not give a full rule
for all modes. & Consume every presented input in its current step.
Unhandled inputs and failed guarded requests have no input-specific
effect. If an autonomous row is selected instead of an enabled input
row, the input is still consumed. No buffering, deferral, or replay
occurs. \\
A04 & The file does not specify simultaneous operator events or whether
enabled autonomous transitions may be postponed indefinitely. & Present
at most one operator event per step. Simultaneous arrivals can be
serialized in any order, with one step per event; the source fixes no
order or intervening sensor evolution. With no operator event, steps
still occur. Take some enabled row on each step; stutter only if no row
is enabled. No fairness or real-time bound beyond this per-step rule is
imposed. \\
A05 & Var5 and Var6 call the indices natural numbers while also
prescribing \texttt{−1}; ties between closest obstacles are not
resolved. & Extend each index domain to \texttt{ℕ\ ∪\ \{−1\}}. Among
equally close obstacles of the appropriate class, use the smallest
natural identifier. The tie rule can affect \texttt{hs}, \texttt{vs}, or
CPA and is an interpretive choice. \\
A06 & DM3 permits a partial function over natural identifiers without
stating finiteness; minimum selection can fail for certain infinite
collections. & Assume every operational obstacle register is finite.
Static classification uses exactly DM2's two horizontal zero tests, even
if an obstacle has nonzero vertical velocity. \\
A07 & DM5 prescribes zero relative-position/velocity accessors for
missing obstacles, while OP5 refers to large-distance defaults without
defining the resulting CPA pair. ``Safe large'' has no numeric value. &
Use the real sentinel \texttt{F} defined above for missing distances and
\texttt{cda}, and choose \texttt{tcpa\ =\ 0} for no dynamic obstacle.
Treat the missing-obstacle case explicitly; do not feed its zero
relative-position accessors into an invented CPA formula. This is a
chosen safe completion, not a formula stated in OP5. \\
A08 & OP5 does not specify relative-velocity sign, two- versus
three-dimensional CPA, treatment of a past CPA, or zero relative speed.
& Leave CPA for existing dynamic obstacles abstract at the mode
interface: provide a nonnegative real \texttt{cda} and real
\texttt{tcpa} each step. Do not clamp negative \texttt{tcpa}, assume a
collision cone, or add a numerical formula. A raw-sensor-level checker
must separately identify its CPA convention; this reference does not
independently validate that convention. \\
A09 & Startup actuator values, OCM entry outputs, exit actions, and
repeated in-mode advice are unspecified. & Emit nothing on startup or
OCM entry unless a selected row explicitly supplies output. Emit MOM/HCM
advice once on each actual entry. Empty-output steps preserve actuator
records. No periodic reissue or exit output is added; initial record
values remain unspecified. \\
A10 & FR4 requires evasive manoeuvres in CAM but specifies no command,
direction, speed, timing, or algorithm. Other general mode descriptions
also do not specify ongoing output schedules. & For this mode-transition
reference, use a minimal output completion: emit only the outputs in the
table, with no additional CAM entry or in-mode output. This does not
specify or discharge FR4's physical manoeuvre obligation. A comparison
of evasive-command algorithms cannot be supported by this file alone. \\
A11 & Descriptive text such as ``potential collision'' or ``reduced
velocity'' could invite extra guards, broader exits, or inferred actions
absent from the numbered behaviours. & Use the numbered guards
literally. In particular, HCM entry advises exactly zero;
\texttt{endTask} acts only in MOM; negative \texttt{tcpa} alone does not
release CAM; and OPEZ alone does not release CAM. No additional
transitions or safety vetoes are inferred from mode names. \\
A12 & DM4 gives defaults but no valid configuration range or
relationship between thresholds. Several guards use literal 1, and some
use different static thresholds. & Keep thresholds as finite real
parameters with default 1 and no added ordering or positivity
precondition. Keep all literal 1 values literal. Require \texttt{F} to
exceed every relevant threshold. No hysteresis or equivalence between
\texttt{V} and \texttt{D} is inferred. \\
A13 & Equality at thresholds and the sign of vertical velocity are
common implementation choices, but the relevant prose here is explicit.
& Use exact real comparisons with the strictness shown in the table; add
no tolerance. Use signed \texttt{vvel\ =\ rate\_of\_climb}, not its
absolute value. This records that no unresolved equality decision was
needed for these guards. \\
A14 & Payload validity, stale data, sensor failures, and numeric
exceptional values are not specified. & Model finite real sensor values
and request payloads and coherent snapshots. Forward OCM payloads
exactly. NaN, infinities, hardware failures, malformed events, and
stale-snapshot recovery are outside this reference's input domain, not
newly invented controller behaviours. \\
A15 & DC1 requires one transition per Beh1--Beh18 and forbids duplicate
source/trigger combinations, yet several behaviours are autonomous exits
from the same mode. & Keep exactly one labelled row per Beh1--Beh18,
including initialization and the two pass-through transitions. Read
source/event uniqueness as applying to explicitly named input events;
retain distinct autonomous requirement rows with their own guards. DC1
supplies no priority or global guard-disjointness rule. If it was
intended to forbid all multiple autonomous exits, it conflicts with the
listed behaviours. \\
A16 & No sampling frequency, environmental evolution, actuator-to-plant
delay, or liveness guarantee is given. Overlapping entry and exit
conditions can cause repeated mode changes across steps. & State only
the per-step relation. Do not promise eventual stability, eventual OCM,
or physical collision avoidance. Permit repeated transitions allowed by
unchanged or changing observations; do not insert dwell times, debounce,
or stabilization logic. \\
A17 & Different enabled rows can have the same destination but different
output obligations. It is unspecified whether their actions should be
merged. & Execute only the selected row's actions plus its
destination-entry advice, as already combined in the table. Do not merge
enabled rows' actions. Preserve row identity when recording a witness;
for conformance compare both destination and output sequence. \\
\end{longtable}

For example, in CAM with input \texttt{reqOCM} and \texttt{cda\ ≥\ s},
both T17 and T18 are eligible, so \texttt{(OCM,\ {[}{]})} and
\texttt{(OCM,\ {[}advVel(0){]})} are both allowed: the move to OCM does
not by itself fix whether velocity advice was emitted.

In MOM, if \texttt{P} and \texttt{C} hold and at least one
static-caution guard holds, OCM, CAM and HCM are all permitted
destinations; HCM comes with \texttt{{[}advVel(0){]}}, the other two
with nothing. This overlap is intended (A02).

With no obstacles, positive depth and no operator input: HCM goes to
MOM, CAM goes to OCM with \texttt{{[}advVel(0){]}}, MOM stays in MOM,
and OCM stays in OCM until a guarded \texttt{reqMOM} arrives. If depth
is not positive, \texttt{P} holds even with no obstacles, so HCM can
have both T13 and T16 enabled.

Nothing guarantees stability, even under constant observations. When
\texttt{D\ \textgreater{}\ V}, an observation with
\texttt{hs\ \textgreater{}\ H} and \texttt{V\ \textless{}\ vs\ ≤\ D}
enables HCM-to-MOM by T13 and then MOM-to-HCM by T10 on the next step;
with no competing guard the modes alternate and the entry advice
alternates between 1 and 0. The requirements permit this, and this
specification does not repair it.

\textbf{Use as an oracle.} A single-step observation conforms exactly
when its \texttt{(destination,\ output\ sequence)} is in
\texttt{R(m,e,x)}, starting from OCM. An implementation with a fixed
priority selects a subset of the allowed alternatives and need not
exercise them all; a mode change or output outside the relation is a
violation under the decisions recorded here. A trace conforms when every
step does; no fairness condition is added.

Differences of priority alone are therefore not detected. Findings that
turn on event consumption, obstacle ties, the missing-obstacle CPA or
unspecified outputs depend on the readings in Table~\ref{tab:ambiguities} and should be reported as such.
The CPA arithmetic for existing obstacles and the effectiveness of
evasive manoeuvres are outside this relation's scope. No extracted
model, mutant, verifier result or kill rate informed the relation.
