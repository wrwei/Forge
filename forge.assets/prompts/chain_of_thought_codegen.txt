STEP-BY-STEP REASONING FOR JAVA SOURCE CODE GENERATION

Read only the requirements file you are given, and generate code for its
requirements only. Every structural rule referred to below is stated in
`java_codegen_rules.txt`; this guide gives the order in which to work. The
examples use a pedestrian-crossing controller, which is not one of the systems
you will be asked to implement.

Each requirement has a `types` list. Work through the types in the order below;
a requirement can have more than one type.

Phase 0 — Annotation

Step 0. Generate the `@RoboChartType` annotation in an `annotation` subpackage
(rules, section 2). Apply it from here on: `@RoboChartType("real")` on every
double field, parameter and return type, `@RoboChartType("nat")` on integers
that are counts or indices.

Phase 1 — Data, events, modes, constants

Step 1. Data types ("data_type"). One record per value type the requirements
name, one enum per finite set of named values. Keep only the fields the
requirements mention.

Step 2. Events ("event"). Two sealed interfaces, `InputEvent` and `OutputEvent`,
with one record per event the requirements name. An event that carries a value
has one record component of the type the requirement gives; a signal has none.

Step 3. Modes ("state"). One enum per controller with one value per mode the
requirements name, the initial mode first.

Step 4. Constants ("constants"). One constants class with a `static final`
field per numeric value the requirements fix, written as a plain decimal
literal, with the requirement's units.

Step 5. Actuators ("actuator"). A class that receives the controller's output
commands and records the last value issued.

Phase 2 — Sensors, functions, operations

Step 6. Sensor quantities ("function", or any requirement that defines a value
read from or derived from the environment). One method per quantity on a class
whose name contains "sensor". Its parameters and return type are those the
requirement gives. If the requirement does not say what to return when no
reading is available, choose a value of the declared type, keep it within the
quantity's range (an integer is never negative), and record the choice as an
`invented_default` in the Layer 5 review.

Step 7. Operations ("operation"). One class per operation, named as the
requirement names it, with a single `compute()` made only of `this.field = expr`
assignments (rules, section 5), and one getter per computed variable.

Step 8. Variables ("variable"). Fields of the controller (or of the operation
that computes them), typed and annotated as the requirement states.

Phase 3 — Controller

Step 9. Guards ("guard_predicate", and every condition a transition requirement
states). List every condition the transitions use. Declare one named boolean
predicate per distinct condition at the top of `step` (rules, section 4a).

Step 10. Transitions ("transition"). For each mode, list the transitions that
leave it, ordered by the priority the requirements give, and write the mode's
block: event-triggered transitions test the event with `instanceof` and then
predicates; autonomous transitions test predicates only; a transition that
applies in several modes is repeated first in each. Every branch assigns the
mode and performs the target's entry actions (rules, section 4b).

Step 11. Architecture and constraints ("architecture", "constraint"). Check the
class structure against the architecture requirements, and check that every
constraint requirement is either enforced by the code or listed in the Layer 5
review as not enforced.

Example: a predicate and a mode block.

    boolean waitAboveLimit = sensor.waitingTime() > CrossingConstants.MAX_WAIT;
    boolean crossingClear = sensor.pedestriansOnCrossing() == 0;

    if (currentMode == Mode.TRAFFIC_GREEN) {
        if (event instanceof InputEvent.ButtonPressed) {
            currentMode = Mode.TRAFFIC_AMBER;
            actuator.showAmber();
        } else if (waitAboveLimit) {
            currentMode = Mode.TRAFFIC_AMBER;
            actuator.showAmber();
        }
    } else if (currentMode == Mode.TRAFFIC_AMBER) {
        ...
    }

An event is tested inline with `instanceof`; it is not a predicate.

Example: an operation.

    public final class ComputeQueue {
        private final Sensor sensor;
        @RoboChartType("nat") private int waiting;
        @RoboChartType("real") private double meanWait;
        public ComputeQueue(Sensor sensor) { this.sensor = sensor; }
        public void compute() {
            this.waiting = sensor.pedestriansWaiting();
            this.meanWait = sensor.totalWaitingTime() / (this.waiting + 1);
        }
        public int waiting() { return waiting; }
        public double meanWait() { return meanWait; }
    }

Phase 4 — Output

Step 12. Write every file (or the JSON manifest, if asked), compile, and write
the trace file described in `codegen_trace_rules.txt`.
