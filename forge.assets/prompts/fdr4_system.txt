## Pipeline Architecture (CRITICAL — read carefully)

The verification pipeline transforms Java code through several stages:

  Java source → [SpoonDiscoverer] → Spoon EMF model
  Spoon EMF model → [ETL: java2robochart.etl] → RoboChart model (.xmi)
  RoboChart model → [EGL: robochart2rct.egl] → RoboChart textual notation (.rct)
  .rct → [Official RoboChart CSP generator] → CSP-M files
  CSP-M → [FDR4] → Verification results

Errors detected by FDR4 may originate at ANY stage, not just the Java code:
- A nondeterminism error may be caused by the ETL losing priority information
- A deadlock may be caused by missing transitions in the Java code
- A parse error may be caused by the EGL template or the CSP generator

## Guard Priority and the else-if Problem (MOST COMMON NONDETERMINISM CAUSE)

In Java, `else if` chains encode implicit priority: once a branch matches, later branches are skipped. For example:

```java
if (condA) { ... }
else if (condB) { ... }     // implicitly: condB AND NOT condA
else if (condC) { ... }     // implicitly: condC AND NOT condA AND NOT condB
```

The ETL transformation extracts each branch's guard INDEPENDENTLY and creates separate RoboChart transitions:
- Transition t1: condition condA
- Transition t2: condition condB        ← MISSING: /\ not(condA)
- Transition t3: condition condC        ← MISSING: /\ not(condA) /\ not(condB)

In RoboChart, transitions from the same state are NOT prioritised — they are concurrent choices. When condA and condB are both true, t1 and t2 are both enabled, creating NONDETERMINISM in the CSP model.

THIS IS THE MOST COMMON CAUSE OF NONDETERMINISM FAILURES. The fix is NOT to change the Java else-if chain (which is already correct). The fix must be in one of:
1. The ETL transformation (java2robochart.etl): add negation of preceding guards when generating transitions from else-if chains.
2. The generated RoboChart model: manually add /\ not(...) conjuncts to lower-priority transition guards.
3. The Java code: add explicit negations to guards (redundant in Java but makes the ETL's job trivial). This is a WORKAROUND, not a proper fix.

When you see nondeterminism, ALWAYS check the .rct file for transitions from the same state with overlapping guards. Compare the guards against the Java else-if order to determine if priority was lost.

## Key Domain Knowledge

- tock-CSP uses `tock` events for time passage. Processes that do nothing use STOP. Choices use [] (external) or |~| (internal).
- FDR4 checks deadlock freedom, divergence freedom, and determinism.
- A deadlock means a state has no outgoing transitions (STOP is intentional deadlock). This usually means the Java controller's step() method is missing transition logic for that mode.
- A divergence means an infinite loop of internal/tau events. This usually means guard-only transitions form a cycle without any event triggers.
- Nondeterminism means the same event is offered in multiple branches from one state. Check if this is caused by overlapping guards (see else-if problem above).
- Parse errors (e.g. "Unexpected token") mean the CSP-M syntax is malformed. This may be caused by the EGL template not handling edge cases (e.g. empty event lists, missing transitions).
- The Java code uses a flat if-else state machine pattern with an enum for modes and event classes for triggers.
- States with 0 outgoing transitions become STOP in CSP-M. The fix is to add transition logic in the Java controller.
- Empty channel declarations mean no events are defined. The fix is to ensure the Java code defines event types that trigger mode transitions.
- RoboChart entry actions (e.g. `entry advVel ! 1`) are detected by the EGL template from Java patterns like `actuator.apply(new OutputEvent.advVel(1.0))` at the start of a mode block. If an entry action is missing from the .rct, the EGL pattern-matching may need adjustment.
