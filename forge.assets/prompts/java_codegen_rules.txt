JAVA CODE GENERATION RULES

These rules define the Java profile the pipeline can turn into a formal model.
They describe the extractor's input language and RoboChart's semantics; they
say nothing about any particular system. Examples use a pedestrian-crossing
controller that is not one of the systems you will be asked to implement.

Requirements: read only the requirements file you are given. Generate code for
its requirements and nothing else.

Target: Java 17, Gradle 8.12+, JUnit Jupiter 5.11+.

1. LANGUAGE FEATURES

Use:
- records for immutable value types;
- sealed interfaces with one record per variant for event types;
- `var` for local variables where the type is obvious.

Do not use (the extractor has no rule for them, or RoboChart has no
counterpart):
- lambda expressions, streams (`.stream()`, `.filter()`, `.map()`, ...), method
  references (`::`) and functional interfaces (`Function`, `Predicate`, ...);
  use imperative loops and direct assignments;
- pattern-matching `instanceof` (`event instanceof Foo f`); write a plain
  `instanceof` test and a cast on its own line:
      if (event instanceof InputEvent.ButtonPressed) {
          InputEvent.ButtonPressed bp = (InputEvent.ButtonPressed) event;
          ...
      }
- switch expressions or switch over patterns;
- ternary conditionals (`c ? a : b`); use if-else;
- `Optional` / `OptionalInt` on any method the controller's guards or actions
  call (the extractor has no type for them); return a value of the declared
  type instead.

2. TYPES AND THE @RoboChartType ANNOTATION

How Java types become RoboChart types:
- `int`, `Integer`, `long`, `Long` become `nat` (a natural number). No Java type
  becomes RoboChart `int`. A Java integer in the model can therefore never be
  negative: do not give an integer field, constant or return value a negative
  value, and do not use a negative number to mean "none" or "unknown".
- `double`, `float` become `real`; `boolean` becomes `boolean`.
- declared enums and records become types of the same name; `List`, `Set` and
  `Collection` become sequences.
- any other type (including `String`) is modelled as `real`, which loses its
  meaning; keep such types out of anything the controller uses.

Generate the annotation in an `annotation` subpackage:
    @Retention(RetentionPolicy.SOURCE)
    @Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.METHOD})
    public @interface RoboChartType {
        String value();
    }
Apply it on field declarations, method parameters and method return types only:
- every `double` field: `@RoboChartType("real")` (required; the profile checker
  reports a missing one as an error);
- an `int` that is a count, index or other non-negative quantity:
  `@RoboChartType("nat")`;
- never on local variables, generic type arguments or other type-use positions
  (it does not compile there).
    CORRECT:  @RoboChartType("nat") private int pedestriansWaiting = 0;
              public double distance(@RoboChartType("nat") int index) { ... }
    WRONG:    @RoboChartType("real") double d = sensor.distance(0);   // local
    WRONG:    List<@RoboChartType("nat") Integer> queue;               // type argument

Constants: write numeric constants as plain decimal literals (`2.5`, `0.001`,
`100000.0`). The model's constants interface rounds a fractional constant up to
the next integer; if the exact value matters to a guard, say so in the Layer 5
review.

3. NAMES

The textual RoboChart notation (.rct) reserves these words (case-sensitive):
    event, state, transition, action, trigger, condition, clock, entry, during,
    exit, module, connection, requires, uses, interface, function, datatype,
    enumeration, var, const, stm, wait
A reserved word may not be used as:
- a parameter name of a sensor or operation method the controller calls;
- a field of the controller (controller fields become state variables);
- a public field of a sensor, actuator or operation class;
- an event (record) name.
It may be used as a local variable, as the parameter name of `step`, and inside
a type name such as `InputEvent`.

Each name in the model must also be unique within its scope: an event must not
share its name with a field, a sensor or operation method, a constant or an
enum value, even when the Java compiler accepts it (for example with different
capitalisation, `ButtonPressed` the event and `buttonPressed` the method).

Substitutes for reserved words: `event` → `value`, `signal`; `state` →
`currentMode`, `status`; `clock` → `timer`; `wait(n)` → `pause(n)` or
`delay(n)` (see 6).

4. THE CONTROLLER

Each controller is one class with:
- a mode field of an enum type (named `mode` or `currentMode`), initialised to
  the initial mode; put the initial mode first in the enum;
- one public method `void step(InputEvent event)`, called once per control
  cycle, that handles both event-triggered and autonomous transitions;
- no event queues, threads, while-loops, transition tables or transition
  records; transitions are not split across several methods.

The body of `step` has two parts.

(a) Named boolean predicates, declared before the if-else chain, one for every
guard condition. The right-hand side is a simple expression built only from:
sensor and operation method calls, constants, arithmetic (+ - * /),
comparisons (< <= > >= == !=), boolean operators (&& || !) and previously
declared predicates. Name each predicate after the quantity, reference and
direction it tests (`waitAboveLimit`, `crossingClear`). Reuse the same
predicate where the same condition appears in several modes; negate with `!`
instead of declaring a second predicate.

(b) A two-level if-else:
- the outer chain has exactly one block per mode, each `currentMode == X`
  (never `currentMode != X`);
- inside a mode block, an inner chain lists that mode's transitions in priority
  order, highest first: an event-triggered transition tests the event with
  `instanceof` and then predicates; an autonomous transition tests predicates
  only;
- a transition that applies in several modes (an override, a stop) is written
  as the first inner branch of each mode where it applies;
- every branch assigns the mode and then performs the target mode's entry
  actions inline;
- a branch below a branch guarded only by predicates (no event test) must
  conjoin the negation of each such earlier guard (`else if (b && !a)`),
  because in the model the branches of a mode are alternatives, not an
  ordered list.

Semantics to keep in mind (RoboChart and its CSP translation):
- a mode with no outgoing transition is a terminal mode; it is valid, and in
  RoboChart's semantics time still passes there;
- a transition with neither an event nor a guard (for example a bare
  `else { currentMode = <same mode>; }`) is an internal step that can repeat
  forever; FDR4 reports it as a divergence. Do not write one.

5. OPERATIONS

A requirement of type "operation" is implemented as a class in an `operation`
subpackage whose name is the operation's name. It takes its sensors (and
constants) in its constructor, has one public `void compute()` method, and
exposes each result through a getter named after the requirement's variable.
The body of `compute()` contains only direct assignments `this.field = expr`,
with no local variables. Each right-hand side is one expression using sensor
calls, `Math.sqrt`, arithmetic, comparisons, boolean operators and fields of the
same class assigned earlier in `compute()`.

6. CONVENTIONS THE EXTRACTOR RECOGNISES

- Clock: a controller field whose type is a class named `Clock`, or a field or
  class annotated `@Clock`. A controller field assigned from a method of the
  clock becomes a RoboChart clock, and `clock.now() - start < LIMIT` becomes
  `since(start) < LIMIT`.
- Sensor service: a class whose name contains "sensor", or a class annotated
  `@SensorService`.
- Waiting: a method named `pause`, `wait` or `delay`, or a method annotated
  `@RoboChartWait`, becomes a RoboChart `wait`.

7. CODE STYLE

No wildcard imports; fields final unless they must change; classes
package-private unless public access is needed; Javadoc on the public API only;
no `System.out.println` outside a demo `main`.

8. PACKAGES

Derive the base package from the system's name. Use the sub-packages `sensor`,
`actuator`, `event`, `controller`, `operation` and `annotation` as needed.

9. OUTPUT FORMAT

When asked for a JSON manifest: {"files": [{"path": "relative/path", "content":
"java source"}]}, paths relative to the project root, each file with its package
declaration and imports, JSON only.
